# 第一部分 · 整体篇

## 1. 它是什么、解决什么问题

需求收集助手是 H5 提报端里的"AI 引导员"。渠道经理、客户经理用手机用大白话说一件事，助手负责把这句话聊成一张**要素齐备、可受理**的需求单。

它要解决三个真实问题：

| 问题 | 助手的对策 |
| --- | --- |
| 提报人不知道"该说什么" | AI 按一张标准清单逐项追问，问法全是大白话 |
| 提报人写得不具体（"好用就行"） | AI 判质后温和追问一次，问不动不纠缠 |
| 提报人说不清组织级理由 | 只问一次"对部门有啥好处"，答不出不拦提交，受理环节兜底 |

一句话定位：**让非技术背景的提报人，用聊天的方式交出一张产品经理能直接用的需求单。**

## 2. 整体运转方式（用户旅程）

```
进页（带草稿/新建）
  → AI 看表单快照，缺什么问什么（对话气泡 + 右侧表单卡实时更新）
  → 必填（A/C/D 三区 10 项）问完 → AI 必问一次 B1："对部门或行里有啥好处不？"
      ├─ 答出 → 落库，判型当场翻转为业务需求（B1 兜底 0.7，见 §4.4）
      └─ 答"不清楚/说不好" → 固定放行书"先空着，不耽误提交"，永不再问
  → 要素齐备 → 弹出「确认提交」选择
  → 提交成功（受理人视角的需求进入待受理池）
      ↓ 若被受理人打回
  → 提报人重进：开场快照引述打回原因（只说一次），按缺口继续聊
  → 补充提交成功 → 该需求的退回角标自动清零
```

全程两条铁律兜底体验：**答不出可以跳过（问满即放过）**、**不影响提交的信息绝不拦人**。

## 3. 系统全景架构

| 层 | 组成 | 职责 |
| --- | --- | --- |
| 前端 H5 | Vue3 + Vant（`frontend/h5`），端口 5174 | 对话气泡、表单快照卡、附件上传、确认提交面板 |
| 后端 API | FastAPI（`server`），端口 8000，前缀 `/demandhub-api` | 会话编排、要素合并、持久化、提交/受理校验 |
| 对话引擎 | `app/agent/`（guide.py 编排 + policy.py 纯函数 + prompts/ 提示词） | 决定"这一轮问什么、说什么、算不算完" |
| 大模型 | 火山方舟（聊天模型 JSON 模式 + Doubao-Seed-2.1-pro 视觉模型） | 只做两件事：从用户话里**抽取要素**、给要素**判质** |
| 数据库 | MySQL（本地 Docker 3308；TEST 环境平台托管） | 需求、会话、消息、附件、通知、流转日志 |

### 架构铁律（第一条设计哲学）

> **模型只做"抽取 + 判质"，决策全归纯函数。**
> 追问哪个字段、说什么话术、能不能提交，全部由 [policy.py](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/agent/policy.py) 的纯函数（不给模型自由发挥空间的固定逻辑）决定。模型输出再花哨，也只是一份"建议补丁"，落地前要过合并保护与规则校验。
> 好处：行为可预测、可单测（577 条后端用例覆盖）、换模型不改业务。

## 4. 核心概念模型（四个词看懂全系统）

### 4.1 五区标准 —— 一张需求单的骨架

每个需求类型对应一份 YAML 标准（如 [tech.yaml](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/standards/tech.yaml)），把要素分成五个区：

| 区 | 含义 | 要素举例 | 是否必填 |
| --- | --- | --- | --- |
| A 公共 | 谁提的、多紧急 | 标题、紧急程度、期望交付时间、原话底稿 | 标题/类型/紧急程度必填 |
| B 业务（Why） | 组织为什么批准这笔投入 | B1 业务目标、业务背景、业务价值、干系人 | **全部非必填**（2026-10-24 拍板解耦） |
| C 用户（Who/What） | 谁用、用来干什么 | 用户角色、用户目标、使用场景、痛点 | 必填 |
| D 功能（How） | 做成什么样、怎样算做完 | 功能描述、输入输出、验收标准、建议方案 | 前三项必填，建议方案选填 |
| E 系统 | 系统自动快照 | 提报人、部门 | 系统回填，不问 |

### 4.2 要素状态机 —— 每个要素四种状态

- **OK**：有值且质检合格；
- **VAGUE**：有值但太笼统（如"好用就行"）；
- **MISSING**：真空着；
- **SKIP**：用户答不出明确跳过（仅非必填要素允许）。

### 4.3 轻重双通道 —— 轻量提报与常规提报

- **轻量（light）**：小改动走捷径，只问少量 MISSING 要素，门槛低；
- **常规（standard）**：完整走完 A/C/D 必填 + B1 白话一问。
- 打回不改变口径（轻量打回仍轻量）；补充期间可在【归类与提报口径】页双向切换，无拦截。

### 4.4 判型 —— 业务/用户/功能需求的归类标签

AI 根据对话给三个倾向分（business/user/function），得出判型标签。**2026-10-24 拍板后判型只作归类展示**：不再驱动 B 区必填、不拦提交；提报人可手动确认或改判，前端 toast 只说"已确认为业务需求"，不再宣称"纳入必填"。

判定规则（2026-10-24 拍板，**层级倾斜 business > user > function** + **档位对齐**）：人工确认（confirmed）优先；未确认时 business ≥ 0.7 → 业务需求；否则 user ≥ 0.7 → 用户需求；否则 → 功能需求。判线贴在模型打分档的「主句级」起点（打分档：0 到 0.3 无信号 / 0.4 到 0.6 从句级 / 0.7 到 1.0 主句级），从句级信号（收益从句封顶 0.6）与判线之间隔着天然空档，模型打分日常波动跨不过线——**哪一层当上整句话的叙事主角，才归哪一层**；function 票不参与比较。模型票数按轮**取历史最高、只涨不跌**（[merge_type_signals](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/agent/policy.py#L120)）。提示词侧两道防误判闸门：多信号叠加不得突破封顶线；受益主体是具体自然人本人（含个人账号/个人副业）时 business 一律按无信号档打分。双保险：**B1 落库即判业务**——B1 从空变为有值时，规则层直接把 business 票补足到 0.7 门槛（[promote_business_on_b1](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/standards/rules.py)），对话轮与详情页手改同口径；模型打分只需同向即可，不依赖模型把分给够。

同一套规则全端三处同口径落地：H5 表单卡归类标签（[FormSnapshotCard.vue](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/frontend/h5/src/components/FormSnapshotCard.vue)）、管理后台需求列表「需求层级」列（[status.ts](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/frontend/admin/src/utils/status.ts) `demandLevelOf`）、管理后台详情页判型置灰（[demand.ts](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/frontend/admin/src/utils/demand.ts) `recognitionLevel`：业务需求全亮、用户需求 B 区灰、功能需求 B/C 区灰、全零视为无判型不置灰）。

## 5. 三条设计哲学

1. **决策归纯函数**（见 §3 铁律）；
2. **规则声明式**：话术、必填声明、追问顺序、跳过词全写在 YAML，改规则不改代码，支持热重载（不用重启应用）；
3. **白话优先**：提报侧话术禁用角色/流程术语——提报人称"你"、受理说"后面负责看的同事/产品经理会处理"、打回说"需要你再补点东西"（完整红线见 §12）。

# 第二部分 · 细节篇

## 6. 一轮对话的完整生命周期

入口是 [guide.py](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/agent/guide.py) 的 `GuideService.execute(trigger=...)`，trigger 有 `dialog / attachment / event / manual / vision` 等分支，一轮消息的处理顺序：

```
用户消息 → ① 调模型（JSON 模式）拿到"结构化补丁 + 要素判质 + 意图"
        → ② merge_structured 合并补丁（来源保护：用户手填的值不被模型覆盖）
        → ②b 判型合并：模型三票与历史取最高（只涨不跌，confirmed 人工定稿不动）；
             本轮 B1「空→有」则 business 票补足到 0.7，判型当场翻转为业务需求（§4.4）
        → ③ inherit_and_count 继承追问计数（同一要素最多问 2 次，问满放过）
        → ④ complete_elements 仲裁要素状态（OK/VAGUE/MISSING/SKIP）
        → ⑤ schema_errors 算提交门槛（固定 A/C/D 三区）
        → ⑥ pick_follow_up 选下一个追问目标
        → ⑦ reply_for 生成话术，按排版规则拼段落
        → ⑧ 消息与表单快照落库（agent_message，幂等防重）
```

**意图分流**（模型判出用户这句话的意图）：聊需求走主流程；打招呼/闲聊给引导语；答不出（整句命中跳过词：不知道/不清楚/说不好/后续补充/再说吧/以后再说/先这样）标记 SKIP 并放行；纯确认走快捷回复。

## 7. 追问引擎 pick_follow_up（决定"下一个问什么"）

规则按优先级从高到低（均在 [policy.py](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/agent/policy.py)）：

1. **急单门控插队**：紧急程度选了"特急/紧急"且期望交付时间为空 → 最优先追问交付时间；只问一次，问后不纠缠，交付时间始终非必填不拦提交；
2. **两遍扫描**：先扫 MISSING（真空着）再扫 VAGUE（有值但质检不达标）——"先补没有的，再修不好的"（2026-10-23 拍板）；组内顺序 A/C/D → B 沉底 → 紧急程度最后；
3. **B1 白话一问**（治理型追问，与急单门控同性质）：`businessGoal` 真空着且从未问过 → 必问一次，**不受"可提交即停问"限制**；
4. **可提交即停问软质量**：必填已齐后，非空但"不够量化"的项不再追问，交给表单卡标黄与受理打回兜底；
5. **问满放过**：同一要素问满 2 次（attempts 达上限）不再追问。

## 8. 话术体系

- **来源**：全部模板写在 tech.yaml（`ask_missing / ask_l1 / vague_hint` 等字段），句式统一"追问句前置 + 例子瘦身 + 引述依据收尾"（2026-10-23 拍板）；
- **锚定追问**：首次追问引用用户已说过的信息，不重复问已知内容；
- **多段拼接排版**（2026-10-23 拍板）：提示/播报类（粒度提示、建议方案播报、打回引述等）之间空行成段，**行动项（追问）沉底离输入框最近**；前端气泡 `white-space: pre-wrap` 原生支持换行，纯服务端改动；
- **完成话术矩阵**：按场景（新草稿/打回补充/手改补齐/附件补传）区分措辞，打回补充口径只承诺"确认提交即可重新提交"，不复读选填项长说明。

## 9. 质量判定与防编造

- **判质**：模型对每条要素给 OK/VAGUE 建议，`complete_elements` 结合规则仲裁（如 B1 只需"说清组织批准理由，≥10 字"，"释放 1 人产能"即合格）；
- **计数**：`inherit_and_count` 只在"值有变化"时记追问次数，手改补齐会被识别并接续下一个缺口；
- **合并保护**：`merge_structured` 带来源标记（user/agent/default），用户手填的值模型覆盖不掉；模型输出的非法值（如日期写"本周"）丢弃而不是整轮报错；把质量状态词（"VAGUE"）当值输出的自相矛盾数据按未输出过滤；
- **数字溯源（FR-08）**：模型整理文本中含不可溯源的阿拉伯数字会被过滤，防止 AI 编造量化指标。

## 10. 轻重双通道细则

- 判重依据：`ext.mode.level = light / standard`；轻量需求只走少量 MISSING 追问，门槛显著更低；
- 修改归类或提报口径与手动改要素同规则：**AI 立即播报变更内容，当场按新规则重算质量卡并接续追问**；要素齐备时直接弹「确认提交」，不延迟到下一轮；
- 打回后口径保持原样，不强制升级；补充期间可双向切换。

## 11. 打回补充闭环（NEED_INFO）

- 受理人打回时填写原因，落在 `ext.returnReason`；
- 提报人重进提报页：开场快照**仅首次**引述打回原因（"这条需求之前被打回过，打回原因是「…」。按这个说明改好后就能重新提交。"），后续不再重复播报；
- 补充期间 AI **不复读全新草稿引导长话术**，只输出对应触发来源的简短行动指引；
- **提交成功即清零**：提交成功时把提报人对该条需求的未读通知全部标记已读，「我的需求」菜单退回角标自动递减清零，不影响其他退回需求的提醒，前端零改动。

## 12. B1 白话一问 · 治理前置（2026-10-24 拍板）

背景：业务目标（B1）是治理关键要素，但提报人（如张征经理）往往说不清组织级目标，强拦会卡死提交。方案是"提报侧白话问一次 + 答不出放行 + 受理侧强校验兜底"：

| 环节 | 规则 |
| --- | --- |
| 触发 | 常规（standard）需求 C/D 区必填问完后必问一次；轻量不问；触发条件是"重量级"而非"用户需求"标签 |
| 问法 | "这个需求做出来，除了你自己省事，对部门或行里还有啥好处不？不清楚也没关系，照实说就行。" |
| 答不出 | 命中"不清楚/说不好"类 → 不追问第二次、不标 VAGUE、不拦提交；固定放行书："没事，这个先空着，不耽误提交，后面的产品经理会一起考虑。"（**绝不承诺"后续找谁补"**） |
| 答出 | 照常抽入 B 区；B1 落库即判业务——规则层把 business 票补足到 0.7 门槛（主句级起点），判型当场翻转为业务需求（层级规则见 §4.4，人工确认过的不动） |
| 话术红线 | 提报侧禁用角色/流程术语：提报人→"你"；受理/待受理→"后面负责看的同事/产品经理会处理"；打回/退回→"需要你再补点东西"；质量缺口/要素→"还差的信息"；B区/业务目标→"为什么做、有什么好处"（写入 [submit_guide.md](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/agent/prompts/submit_guide.md) 并附张征案例反例） |
| 受理兜底 | 常规科技需求受理（ACCEPT）前 B1 必填，缺则 400 拒绝受理，提示详情页补录或打回；轻量微需求不受限（[triage_service.py](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/services/triage_service.py#L132)） |
| H5 表单卡 | B 区不标红星；B1 空缺显示灰字"先空着，不影响提交"（不挂待办不标红，不说"会补"）；折叠态不再显示"业务 X/Y"进度（[FormSnapshotCard.vue](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/frontend/h5/src/components/FormSnapshotCard.vue)） |
| 口径放宽 | B1 从"组织/部门的量化指标"放宽为"组织批准这笔投入的理由"，≥10 字即可 |

同时完成的解耦：B 区四件套（B1/背景/价值/干系人）全部非必填；提交门槛固定 `active_zones={"A","C","D"}`；判型标签仅作归类展示；`businessConfirmed` 保留作判型翻转确认，不再关联提交拦截。

## 13. 附件与图片理解（vision）

默认口径：**AI 不看附件内容**。只有用户显式点「让 AI 读懂图片」入口上传时，视觉模型才读取该图片；「拍照或选择图片」「上传文档」入口仍是纯存档。

- **两步走**：视觉模型只做"图 → 文本"转写（[vision_service.py](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/services/vision_service.py)），转写文本包装成用户消息走 `GuideService.execute(trigger="vision")`，完整复用既有判型/抽取/追问链路，话术统一加前缀"我从图片里读到了内容，先帮你整理了一下。"；
- **必压缩**：长边超 1600px 缩到 1600 并重编码 JPEG（质量 85），只压缩送模型的载荷，附件原件不变（实测微信原图直送 30s+ 超时）；
- **模型配置**：Doubao-Seed-2.1-pro，`LLM_VISION_MODEL / LLM_VISION_TIMEOUT_S=60 / LLM_VISION_MAX_TOKENS=4096` 独立三项；显式 `thinking=disabled`（同一张 3834px 长截图 92.5s→5.3s）；模型为空即未启用，自动降级为普通附件；
- **降级矩阵**：无文字 → NO_TEXT；LLM 不可用/超时/未知异常 → FAILED；内容审核拒绝 → FAILED + 1405 直达；所有降级路径自动转普通附件，用户无感；
- **入库**：`demand_attachment` 表新增 `purpose / parse_status / parsed_text / parsed_at` 四列（迁移 0016）；解析图片占现有 5 个附件限额、走同一权限矩阵；解析成功时附件气泡展示"AI 已读取"标签；
- **编排位置**：视觉编排放附件落库事务提交之后执行，避免最长 60s 的视觉等待持有需求行锁/会话锁。

## 14. 提交门槛与受理侧兜底

- **提交**（[demand_service.py](file:///c:/Users/liuqu/Desktop/Projects/DemandHub/server/app/services/demand_service.py) `submit()`）：固定校验 A/C/D 三区必填，B 区空缺不拦；
- **受理**（triage_service.accept）：常规科技需求缺 B1 → 400"该常规需求缺「业务目标」（B 区），受理前请先补录：可在详情页直接补录后受理，或打回让提报人补充"；轻量不受限；
- 提报端被拦时（仅剩 A/C/D 缺口的可能）：前端只显示服务端返回的缺项文案，不再有"改判逃生口"；轻量被拦时追加轻量指引 toast。

## 15. 前端 H5 交互要点

## 16. 数据持久化

| 表 | 用途 |
| --- | --- |
| `demand` | 需求主表：五区要素 JSON、ext（判型/模式/打回原因/概述）、状态机字段 |
| `agent_session` / `agent_message` | 会话与消息持久化：幂等写入、structured_payload 快照、prompt 版本留痕 |

**进页快照有效性双重匹配**：除校验 revision 与当前规则模板一致外，还校验快照要素键集合与当前模板完全相等；老版本规则模板生成的存量快照自动判失效，系统纯规则重算生成新快照，避免直接跳过追问流程。

## 17. 可靠性与安全设计

- **LLM 调用**：聊天模型强制 JSON 模式（保证输出可解析）；`max_tokens=8192`（避免长输出截断导致 JSON 解析失败）；显式 `thinking=disabled`（与 dev 对齐，避免深度思考超时 1401）；日志同步输出 stdout 保证平台采集；
- **密钥**：LLM API Key 只走环境变量，不入库不入库代码仓；
- **幂等**：草稿创建 clientRequestId 幂等；消息写入幂等防重；
- **容错**：模型非法值丢弃不整轮报错；视觉调用超时类不自动重试、连接级故障秒级重试一次；
- **规则热重载**：五区标准配置表原子替换，坏配置跳过，空表回落内置兜底，无需重启。
